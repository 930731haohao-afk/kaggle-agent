# 期中報告 — Kaggle 競賽 AI Agent
### 2026 年 7 月成果回報

作者:黃威昊 · 指導:顏佐榕 · 日期:2026-07-28

---

## 1. 研究動機(Motivation)

### 1.1 核心問題

自動化機器學習競賽求解的 AI agent 近年進展快速,但**如何判斷一個 agent 真的比另一個好**,方法學上仍相當薄弱。本研究處理三個相互纏繞的問題。

**問題一:自建 agent 的實際能力位置為何?**

本專案以 Claude Code Skill 實作了一個混合式 Kaggle agent(LLM 推理 + Auto-ML 工具)。它在單場競賽上能產出合理成績,但「合理」是相對誰而言?缺乏外部參照,任何自評都只是自說自話。需要與**性質不同**的既有方法對照,才能定位這套設計的強項與盲點。

**問題二:agent benchmark 的結論有多少是雜訊?**

現行 agent 評測普遍以「單次執行、單一分數、誰高誰贏」呈現。但競賽指標本身有抽樣誤差,agent 執行本身有隨機性(LLM 每步取樣不同的程式碼)。若兩個 agent 的差距小於這些誤差,「A 勝 B」就是在報導雜訊。本研究要問:**在可量測的誤差尺度下,三方 agent 究竟有幾場真的分得出高下?**

**問題三:什麼樣的實驗設計才能避免污染?**

三個 agent 共用一台機器、共用資料目錄、由同一個人配置,任何一個環節疏漏都會讓比較失效——一方讀到另一方的中間產物、一方在資源爭搶下執行、一方的方法被指令悄悄截斷。這些失效**不會報錯**,只會產出看似正常的數字。本研究把「如何讓比較不失效」本身當成研究對象。

### 1.2 為何值得做

Kaggle Playground 系列提供了罕見的評測條件:任務同質(表格式監督學習)、指標明確、有公開排行榜作為外部絕對基準,且每場都有 **public / private 兩個互斥測試子集**——後者正是本研究用來估計量測誤差的關鍵。

## 2. 研究方法(Methods)

### 2.1 my-agent:混合式 Kaggle Agent

本方法以 **Claude Code Skill** 形式實作(`kaggle-agent`),核心設計是 **LLM 推理與 Auto-ML 工具分工**:

| 職責 | 承擔者 |
|---|---|
| 問題理解、驗證策略設計、特徵工程創意、結果詮釋、決定下一步 | Claude Code(LLM) |
| 模型選擇、超參數優化、堆疊/集成 | LightGBM / XGBoost / CatBoost / Optuna(由 LLM 透過 Bash 呼叫) |

執行流程分六階段:**資料匯入 → EDA → 特徵工程 → 建模 → 評估 → 提交**,其中第四至五階段有兩種最佳化模式:

- **線性迭代協定**:逐次提出假設、實驗、記錄,作為第一輪與小型競賽的模式
- **樹搜尋(首選)**:一旦線性協定產出 baseline 單模與至少一個 blend,即切換到樹搜尋(harness v3)。內部評測顯示樹搜尋在 10 場中 9 勝 1 平 0 敗

兩個支撐機制:

**跨賽經驗庫**(`knowledge/experience.md`):每則洞見必附證據欄(`競賽, exp #N, 分數A→分數B`),未附分數差的一律不收錄。agent 在 EDA 前與建模前查詢,實驗結束後把驗證過的新洞見寫回。這是 my-agent 與另外兩個方法**最根本的設計差異**。

**實驗紀錄**(`experiments.json` / `experiments_tree_v3.json`):每次實驗的參數、特徵、切分方式、分數全部結構化記錄,使報告中的每個數字都可追溯。

### 2.2 兩個參照方法(Yardsticks)

**AIDE**(開源 agent,gen-1):LLM 驅動的樹搜尋。每步寫出完整解法、執行、讀取錯誤或分數、據以變異。無跨賽記憶——每場從零開始,journal 僅在單次執行內有效。以其預設預算 **20 步**執行。

**NVIDIA Kaggle Agent**(skill):方法為「複現最強公開 kernel」——研究競賽脈絡、依**票數**挑選最高票的解法型 kernel、忠實移植、在本地資料重訓。知識來自每次現抓的公開解法,無跨賽累積。

**關鍵方法學決策:兩個參照方法一律凍結,不做任何改良。** 研究過程中發現 NVIDIA 依票數選 kernel 是其結構性弱點(見 §3.5),skill 本身也附有依分數選擇的工具,但**刻意不啟用**。理由:本研究的目的是拿它們當固定量尺衡量 my-agent,中途改良量尺會使前後數據不可比,並讓 benchmark 悄悄變成對參照方法的優化。

### 2.3 公平性協定

三方共用機器,故訂定並以機制強制下列規則:

| 面向 | 規則 | 強制方式 |
|---|---|---|
| 資料隔離 | 各方只讀 `bench-comps/<comp>/`,內含 Kaggle 官方 manifest 驗證過的檔案 | `build_isolated_roots.py`,officialness 依 Kaggle API manifest 判定,並辨識官方壓縮檔的解壓成員 |
| 工作區隔離 | 三方輸出目錄完全分離,各自獨立評分 | 目錄結構 |
| 指令隔離 | prompt 只可含環境事實與指標門檻;禁寫任何建模配方、他方分數、他方發現的環境解法 | 人工協定 + 事故紀錄 |
| 資源隔離 | **任一時刻只有一條 lane 執行** | `lane_lock.sh` 互斥鎖(目錄原子建立、持有者死亡自動回收、等待有上限) |
| 環境缺陷 | 一律**修環境**而非給提示(修環境消除變因,給提示只補償單方) | — |

## 3. 實驗(Experiments)

### 3.1 實驗設計總覽

**評測集**:**18 場**表格式競賽——Kaggle Playground Series 13 場,加上 afsis-soil-properties(2014,光譜迴歸)、conway-s-reverse-game-of-life(2014,結構化多輸出)、cat-in-the-dat(2019,純類別特徵)、tabular-playground aug-2022 與 jan-2022。每場皆同時具備 public 與 private 兩個測試子集分數——此為納入本報告的門檻,因為顯著性檢定(實驗二)建立在兩個子集的分數差之上。三方另跑過 4 場無法取得 private 分數的競賽(late submission 關閉、入門賽滾動榜等),不納入本報告;其中 s6e7 於 2026-07-31 賽事結束、private 分數揭曉後可併入。

**執行條件**:三方序列執行,互斥鎖保證不重疊。AIDE 20 步(其預設預算;conway 因 4 小時上限止於 16 步);NVIDIA 依其方法複現公開 kernel;my-agent 走完整六階段含樹搜尋(各場 25–80 節點)。

若採「誰數字大誰贏」的裸計數,結果約為 my-agent 7 勝、NVIDIA 7 勝、AIDE 4 勝。**但這個數字不可信**——理由見實驗二。

### 3.3 實驗二:配對顯著性檢定(本研究的方法學核心)

**為何做**:上表多場的前二名差距在小數點第四、五位(s5e10 差 0.00003、s6e2 差 0.00000)。這種差距是否超過量測誤差?若否,「勝負」就是雜訊。

**如何做——誤差尺度取自資料本身,而非假設**:

Kaggle 將測試集隨機切成 public 與 private 兩個互斥子集,同一份提交在兩者各得一分。**同一模型的兩個獨立估計**,其差距即該場指標的抽樣噪音。

**第一版嘗試失敗,值得記錄**:最初以「單一 agent 自身的 public↔private 落差」為門檻,結果 10 場中 8 場判為平手。原因是該落差**絕大部分由三方共有**——哪些列落在哪個子集會讓所有人一起漂移。s5e10 三方漂移為 +0.00025 / +0.00026 / +0.00024:共同位移 0.00025,彼此散布僅 **0.00002**。以共同位移當門檻,等於把真噪音放大十餘倍,是拿未配對的尺度去衡量配對的問題。

**正確做法**:量測「**兩個 agent 之間的差距**」在兩個子集間移動多少——共同漂移在相減時抵消。判定需同時滿足:

1. `sign(d_priv) == sign(d_pub)`:順序在互斥樣本上重現
2. `|d_priv| > |d_priv − d_pub|`:差距大於差距自身的移動量

**共同漂移的實證**(節錄):

| 競賽 | my-agent 漂移 | NVIDIA 漂移 | AIDE 漂移 | 共同位移 | 彼此散布 |
|---|---|---|---|---|---|
| s5e10 | +0.00025 | +0.00026 | +0.00024 | +0.00025 | **0.00002** |
| s6e2 | +0.00149 | +0.00160 | +0.00152 | +0.00154 | 0.00011 |
| s3e11 | +0.00063 | +0.00065 | +0.00056 | +0.00061 | 0.00009 |
| s3e7 | −0.00859 | −0.00772 | −0.00825 | −0.00819 | 0.00087 |

七場的彼此散布小於共同位移的一半,漂移為共同現象一事成立。

**結果**(18 場 × 每場 3 組配對 = 54 組對決,40 組可判定):

| 方法 | 勝 | 敗 | 勝率(不含平) |
|---|---|---|---|
| **my-agent** | 16 | 11 | **59%** |
| **AIDE** | 11 | 13 | 46% |
| **NVIDIA** | 13 | 16 | 45% |
| 平手 | — | — | 14 組(26%) |

**詮釋**:my-agent 領先,AIDE 與 NVIDIA 在誤差範圍內難分。**四分之一的對決在此檢定下無法分辨**——若不做這層檢定而直接報裸計數,這部分「結論」實為雜訊。值得注意的是,此排名對樣本組成敏感:僅計 Playground 13 場時為 NVIDIA 58% / AIDE 47% / my-agent 44%,加入 5 場非 Playground 競賽後完全反轉(詳見 §4.3)。

**此檢定的已知限制**:它只涵蓋**測試集抽樣噪音**,未涵蓋 **agent 執行間變異**(AIDE 每步由 LLM 重新取樣程式碼,該項應更大)。後續的重複性實驗即為量測此項。

### 3.4 實驗三:本地 CV 與排行榜的結論不一致

**為何做**:隨附的逐場規格報告(附錄 A.1)是在**本地 CV** 上比較三方的,而實驗一、二用的是**實際排行榜**。
若兩者結論一致,CV 就是可靠的代理指標,agent 評測不必付出上榜的成本;若不一致,則所有以 CV 為準的 agent
benchmark 都需要重新檢視。這個對照是免費的——兩份數據都已存在。

**結果:13 場中有 10 場不一致**(此對照限於逐場規格報告涵蓋的 Playground 13 場)。最劇烈的是 s3e19:

| 依據 | my-agent | NVIDIA | 判定 |
|---|---|---|---|
| 本地 CV(TimeSeriesSplit,雙方同切分) | 10.02 | 13.72 | **我方大勝** |
| private leaderboard | 50.46 | 48.27 | **NVIDIA 勝** |

方向完全相反。同一場競賽,CV 說我方領先 3.7 分,LB 說我方落後 2.2 分。其餘不一致的形態包括:CV 判平手而
LB 分得出高下(s3e7、s3e9、s3e11、s5e10、s6e1),以及 CV 判單方勝出而 LB 判平手(s3e14、s3e16)。

**為什麼會這樣**。CV 與 LB 量的是不同的東西:CV 是「在訓練資料的重抽樣上表現如何」,LB 是「在一批從未見過的
資料上表現如何」。兩者在分布穩定時高度相關,一旦測試集與訓練集的關係改變就會脫鉤。s3e19 正是極端案例——
三方的 CV 都在 10–14,LB 卻都在 48–50,**全體同時失準**,而失準幅度的排序與 CV 的排序無關。該場排行榜為
雙峰分布(1174 隊中 265 隊低於 10 分、570 隊落在 40–60),三方全部落在下峰,CV 無從預測這件事。

**方法學意涵**:這是本研究主張「agent benchmark 必須上實際排行榜」的直接證據。以 CV 比較 agent 便宜且方便,
但在 13 場中有 10 場會得到與真實表現不同的結論。隨附的逐場報告因此標明其比較為 **CV-only**,其結論不應與
本報告表 3-2b 的排行榜判定混用——兩者不是同一個問題的兩種答案,而是兩個不同的問題。

---

### 3.5 實驗四:失效模式分析

**為何做**:分數表無法回答「為什麼」。逐場檢視三方的執行紀錄與冠軍程式碼,可辨識出方法層級的系統性弱點——這些對 agent 設計的價值高於名次。

#### 3.4.1 AIDE:能診斷,但無機制讓診斷否決分數

**s3e16**:AIDE 於第 16、18 步自行執行 nested-CV,量得校準值為 1.3396 / 1.3412,並在自己的報告中寫下「in-sample 數字偏樂觀」,**最終仍選擇了 in-sample 節點**。private LB 為 1.34224,證實它自己丟棄的誠實估計才是對的。

**s3e19**:更嚴重。指標軌跡在單一步驟內從 18.42 跳到 4.41:

```
step 0–10 : 18.42 … 22.20 … 18.42   (時序驗證)
step 11   : 4.41                     ← 引入 KFold(shuffle=True)
step 12–19: 4.40, 4.37, 4.40, 4.49   (九步在打磨洩漏的數字)
```

第 11 步的計畫本是修正 LightGBM API 相容性問題,重寫訓練迴圈時**順帶把驗證切分換成打亂的 KFold**。SMAPE 定義前後完全相同。本研究以控制實驗確認(同特徵、同模型、僅換切分):

| 切分 | SMAPE |
|---|---|
| `KFold(shuffle=True)` | 4.56 |
| 2017–2020 訓練 → 2021 驗證 | 20.41 |

**4.5 倍**。該競賽測試集為未來一整年,打亂列使模型得以在已記憶的序列中內插。AIDE 對此毫無察覺,其後九步全部用於對假指標調參。

**對照**:my-agent 在同場亦嘗試過打亂 KFold(SMAPE 4.2814),但在 `experiments.json` 中明確標註「**DIAGNOSTIC: not used for submission**」,用途是隔離「分數變差是因切分還是因特徵」。同一個陷阱,一方誤用、一方隔離。

#### 3.4.2 NVIDIA:票數不等於品質

其方法以票數挑選 kernel,而票數量測的是人氣與教學價值:

| 競賽 | 複現的 kernel | 票數 | 結果 |
|---|---|---|---|
| s3e19 | `tumpanjawat/s3e19-course-eda-fe-lightgbm` | — | 48.27,榜首 4.67 |
| s3e3 | `chunweishen/ps-s03e03-ensembling` | 89 | 三方最佳 |

僅 89 票的實戰解法拿下三方最佳,而高票 kernel 常是教學導向而非競賽導向(本報告之外的一場入門賽中,7859 票的教學 kernel 使 NVIDIA 三方墊底)。此外 s3e19 那份 kernel 檔頭聲稱「與第二名同思路」,NVIDIA 忠實複現其骨架卻漏掉決定勝負的年度縮放——**方法中沒有任何步驟會拿複現分數與來源宣稱名次對照**。

#### 3.4.3 三方共同缺口:外部資料的識別

s3e19 排行榜為雙峰分布:1174 隊中 265 隊得分低於 10,570 隊落在 40–60,10% 分位為 6.1 而 25% 分位已跳至 22.8。三方(48.3 / 49.6 / 50.5)全部落在下峰。該場公認解法需引入各國 GDP 資料。

**但這並非能力上限**:同型題 `tabular-playground-series-jan-2022` 上,my-agent **主動引入世界銀行 GDP per capita** 資料(CV SMAPE 4.1793),AIDE 僅用官方資料自行搜出日曆與黑色星期五特徵(6.1551)。s3e19 是該場的失誤,不是題型的天花板。

### 3.6 實驗五:實驗設計本身的失效與修正

本研究過程中發現五類**不會報錯**的失效,均已修正並機制化。此節本身即為研究成果之一。

| # | 失效 | 影響 | 偵測方式 | 修正 |
|---|---|---|---|---|
| 1 | harness 將 my-agent 的工作目錄整個複製給 AIDE,使其讀到他方的處理後特徵與調好的超參 | 4 場 AIDE 成績作廢 | 逐場檢查冠軍程式實際開啟的檔案 | 建立 manifest 驗證的隔離根;4 場已重跑 |
| 2 | 資源爭搶下執行(某 lane 在 load 17 下跑同一場,另一 lane 獨佔機器) | 條件不對等 | 比對各 lane 執行時段 | `lane_lock.sh` 互斥鎖 |
| 3 | 監看程序以「機器整體是否忙碌」判斷健康,某條 lane 死亡整夜未被發現 | 損失一夜產能 | 逐 driver 檢查(狀態檔無完成標記且無進程) | watchdog 加逐 driver 判定 |

|---|---|---|
| 樹搜尋節點 | **0** | **80** |

修正後不僅分數更好,**耗時反而更短**——與 skill 中「樹搜尋 9 勝 1 平 0 敗」的內部證據一致。

## 4. 討論(Discussion)

### 4.1 本研究達成的成果

1. **完成三方 agent 的可信對照**:18 場具備顯著性檢定條件的競賽,三方各以完整方法執行,結果為 my-agent 59% / AIDE 46% / NVIDIA 45% 勝率,四分之一對決無法分辨。
2. **建立適用於 agent benchmark 的配對顯著性檢定**:誤差尺度取自 Kaggle 自身的 public/private 切分,不需額外實驗即可判定勝負是否超過雜訊,並實證了「共同漂移」的存在與其對未配對估計的破壞。
3. **證實本地 CV 不是排行榜的可靠代理**:13 場中 10 場的三方結論不一致,s3e19 甚至方向相反(CV 我方大勝、LB 我方落後)——以 CV 比較 agent 便宜,但會系統性地得到不同結論。
4. **辨識出三種方法各自的系統性弱點**:AIDE 缺乏讓診斷否決分數的機制;NVIDIA 的選擇訊號(票數)與品質脫鉤且無複現後驗證;三方皆缺乏「本題是否需要外部資料」的判斷。
5. **產出可複用的公平性基礎設施**:manifest 驗證的隔離根、lane 互斥鎖、雙訊號 watchdog、確定性事實抽取。

### 4.2 三種方法的比較

三者的差異不在調參技巧,而在**知識從何而來**與**如何決定下一步**。

| 面向 | my-agent | AIDE | NVIDIA |
|---|---|---|---|
| 知識來源 | 跨賽經驗庫(累積) | 無(每場從零) | 每次現抓的公開 kernel |
| 搜尋策略 | 六階段流程 + 樹搜尋(25–80 節點) | 樹狀試錯 20 步 | 不搜尋,忠實複現 |
| 決定下一步的依據 | 經驗庫先驗 + OOF 診斷 | 上一步的錯誤或分數 | 票數最高的 kernel |
| 驗證嚴謹度 | 依題型選切分,診斷實驗明確標註排除 | 無切分合法性概念 | 沿用 kernel 的切分 |
| 外部資料 | 會主動引入(jan-2022 的 GDP) | 從不考慮 | 繼承自 kernel |
| 配對勝率(18 場) | **59%** | 46% | 45% |

**各自的強項**

**NVIDIA 強在「站在巨人肩上」而非自身推理**。它在 s3e3、s3e7、s3e9、s3e14、jan-2022 勝出,共同點是這些競賽存在成熟的高品質公開解法。它省去了整個探索過程,直接取用社群數百人時的成果——這在有現成好解法時極有效率;在 Playground 13 場子集內它的勝率甚至是三方最高(58%)。

**AIDE 的長處是搜尋深度**。s3e11 是它唯一的全序第一,而該優勢來自一個 bug-fix 節點意外啟用了原生類別處理——換言之,大量試錯本身會撞出人不會想到的組合。它不需要任何外部知識即可運作。

**my-agent 的長處是驗證嚴謹度與知識累積**。s5e10、s6e1 兩場全序第一,s3e5、s3e16 亦居前。更重要的是方法論層面:s3e19 同一個打亂 KFold 陷阱,AIDE 誤用為正式提交(4.5 倍樂觀偏差),my-agent 將其標註為「DIAGNOSTIC: not used for submission」並排除。這種區別不會顯示在單場分數上,卻決定了在未知新題上的可靠度。

**各自的限制**

**NVIDIA 的瓶頸是選擇訊號**。票數量測人氣而非品質:s3e3 奪冠靠的是僅 89 票的實戰解法,高票 kernel 反而常是教學導向(§3.4.2)。且複現後不與來源宣稱的名次對照,s3e19 抄到骨架卻漏掉決定勝負的年度縮放而不自知。無公開解法可抄時,此法無從施展。

**AIDE 的瓶頸是缺乏「讓診斷否決分數」的機制**。它有能力產出正確診斷——s3e16 自行跑 nested-CV 並寫下「in-sample 偏樂觀」——卻仍選擇了樂觀節點。s3e19 更是自己的指標一步跳好 4 倍而全無警覺。它優化的是「顯示出來的數字」,不是「真實表現」。

**my-agent 的瓶頸是問題識別層級的判斷**。經驗庫收錄的是已驗證的技巧(「MAE 題用 L1 目標」),但 s3e19 需要的是「此題需要外部資料」這種前置判斷,經驗庫對此無著力點——jan-2022 它引入了 GDP 卻仍敗給 NVIDIA 複現的 kernel,顯示「有對的想法」與「把想法做到位」之間仍有落差。且其 59% 領先集中來自新增 5 場(該子集 9 個可判定對決取 8 勝),Playground 13 場內僅 44%,樣本相依性見 §4.3。

**共同限制**:三者在 s3e19 全部落入雙峰分布的下峰(48–50 分,榜首 4.67),皆未識別出該題需引入 GDP 資料。而同型題 jan-2022 上 my-agent 做到了(CV SMAPE 4.1793)、AIDE 純用官方資料亦達 6.16——顯示這是該場的失誤,而非題型天花板。

### 4.3 排名不是方法的性質,是「方法 × 評測集」的性質

本研究過程中得到的最重要的方法學教訓:**同一組 agent、同一套檢定,換一批競賽,排名完全反轉。**

| 評測集 | my-agent | AIDE | NVIDIA |
|---|---|---|---|
| Playground 13 場 | 44%(末) | 47% | **58%**(首) |
| 加入 5 場非 Playground 後(18 場) | **59%**(首) | 46% | 45%(末) |
| PR 中位數(13 場) | **74.3** | 73.3 | 66.8 |
| PR 中位數(18 場) | **72.3** | 70.8 | 66.7 |

勝率排名反轉的機制清楚可辨,且與各方法的知識來源直接對應。新增的 5 場中有 3 場是**老競賽或非主流賽制**(afsis 2014、conway 2014、cat-in-the-dat 2019):這些場次的公開 kernel 或者陳舊、或者教學導向,NVIDIA 的「複現最高票 kernel」失去了它在 Playground 系列所享有的成熟解法生態,PR 掉到 18.8(afsis)、32.6(cat)。my-agent 在這 5 場的 9 個可判定對決中取 8 勝——不是因為它變強了,而是因為**對手的前提條件消失了**。

兩點觀察:

1. **PR 中位數在兩個評測集上排序一致**(my-agent > AIDE > NVIDIA),配對勝率則反轉。絕對位置指標比相對勝負穩定,因為後者把大量接近平手的小差距二值化,對樣本組成高度敏感。
2. **「哪個 agent 較強」這個問題本身不完整**。正確的問題是「在什麼樣的競賽分布上較強」:有成熟公開解法的題,複現法(NVIDIA)佔優;冷門題、老題、需要自建 pipeline 的題,自主方法(my-agent)佔優。任何單一數字的 benchmark 排名都隱含了一個未言明的競賽分布假設。

**方法學上的意涵**:agent benchmark 的結論必須連同評測集的組成一起陳述,且應報告絕對(PR)與相對(配對勝率)兩種指標——本研究兩個評測集的對照正是這個主張的直接證據。

### 4.4 實驗設計的限制

- **顯著性檢定僅涵蓋測試集抽樣噪音**,未涵蓋 agent 執行間變異。AIDE 該項預期最大(每步由 LLM 重新取樣程式碼),納入後現有 40 組決定性結果可能有部分退回平手。
- **經驗庫造成的不對稱未消除,僅予揭露**。my-agent 帶跨賽記憶、另二者冷啟動——此為設計差異而非瑕疵,但影響結論的詮釋。
- **樣本數偏小,且 §4.3 顯示排名對評測集組成敏感**。18 場 54 組對決,59% 與 45% 的差距在此樣本量下仍屬粗估;任何單場的增減都可能移動一至兩個百分點。

### 4.5 尚未完成的工作與未來方向

**進行中:**

1. **擴大可檢定集**:afsis、cat-in-the-dat、conway、aug-2022、jan-2022 五場已完成三方並納入本版(即 18 場);s6e7 於 7/31 結束、private 分數揭曉後併入成 19 場。
2. **重複性實驗**:選取勝負最接近的 5 場(s6e2、s4e11、s5e10、s3e16、s3e11),各重跑 AIDE 兩次,量測執行間變異並產出誤差棒。此為 §4.4 首項限制的直接補救。
3. **中複雜度賽事對照**:us-patent(NLP)、ventilator(時序)、SIIM-ISIC(影像)三場,在完全獨佔機器的條件下重跑三方,檢驗結論是否延伸至 Playground 以外的題型。

**未來方向:**

- **讓經驗庫涵蓋「問題識別」層級**:目前收錄的是技巧(「MAE 題用 L1 目標」),缺少「此題型是否需要外部資料」「此題的測試集是否為未來時段」這類前置判斷。s3e19 的失誤正落在此缺口。
- **引入驗證閘門**:AIDE 的兩個失效(s3e16 選擇樂觀節點、s3e19 對洩漏指標調參)皆源於「無機制讓診斷否決分數」。my-agent 可加入強制規則——指標單步改善超過某門檻時,自動觸發切分合法性檢查。
- **選擇訊號的研究**:NVIDIA 的瓶頸(票數 ≠ 品質)是可改進的具體機制。my-agent 不受量尺凍結限制,可實作依作者名次、kernel 自述分數選擇,並在複現後與來源宣稱分數對照。
- **量測經驗庫的實際價值**:目前僅知其存在造成不對稱,未知其貢獻幾分。可設計停用經驗庫的對照組直接量測。

**嚴禁對時序資料使用打亂 KFold。** AIDE 在 s3e19 因一次無關的 bug 修正順帶換成打亂 KFold,本研究以控制實驗

但明確標註為診斷用途並排除於提交之外——同一個陷阱,一方誤用、一方隔離。

### B.4 重現本研究的最小步驟

```bash
# 1) 建立隔離資料根(依 Kaggle 官方 manifest)
python ai_agents/bench-comps/build_isolated_roots.py --write <comp>

# 2) my-agent 單場
cd ai_agents/kaggle && claude -p "<see run_myagent_headless.sh PROMPT>" --dangerously-skip-permissions

# 3) AIDE 單場(20 步)
AIDE_COMP_ROOT=~/ai_agents/bench-comps python ai_agents/aideml/run_comp.py <comp> --shim --steps 20

# 4) NVIDIA 單場
cd ai_agents/nvidia-kaggle-runs/<comp> && python reproduce.py

# 5) 提交並取回 public/private 分數
KAGGLE_API_TOKEN=$(cat ~/.kaggle/huang_token) kaggle competitions submit -c <comp> -f submission.csv -m "<msg>"
```
